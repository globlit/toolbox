# Security model

## Guarantees and trusted components

Within the exposed CLI/MCP API, requests can reach only catalog reads and finite single-pod logs. The policy rejects other verbs, unknown options, subresources, arbitrary raw paths, multi-resource requests, and unsupported resources. The catalog pins API groups and versions. The integration constructs exact resource/log GET paths and URL-encodes selectors and log parameters; only these internally generated paths reach `kubectl get --raw`. User-provided raw paths and flags are rejected. This avoids kubectl discovery falling back to a different group when a core resource is absent.

The trusted computing base includes toolbox, the pinned Go dependencies, the configured native kubectl executable, the OS, operator configuration, and the Kubernetes API server. Protect their files and parent directories against agent modification. Runtime config selection was removed in v0.2. The operator build pins the config path and config/kubectl digests. Caller flags, environment variables, and writable fallback directories cannot select a different config. The same bytes are verified and parsed; a changed config fails before any subprocess starts. The runner checks kubectl content and native format before execution. A plain build without trust anchors refuses requests. Install a supported, patched kubectl separately; the wrapper checks its approved hash but does not establish its provenance or automatically upgrade it. Reprovision after changing config or kubectl. Digest checks do not eliminate the verification-to-execution race on writable executable paths; OS permissions must prevent concurrent replacement. An agent that can replace the trusted gateway itself or execute arbitrary programs with privileged credentials remains outside the boundary. The wrapper assumes an honest API server whose GET endpoints obey Kubernetes semantics. It does not sandbox a compromised kubectl executable or malicious API extension.

Three separate controls are required:

1. **Request enforcement:** this code's closed operation catalog prevents agent tool calls from reaching write commands.
2. **Cluster enforcement:** use a dedicated identity with explicit `get`/`list` and `pods/log` permissions. Kubernetes RBAC permissions are additive; confirm the identity has no other grants. A restricted token still prevents writes if someone bypasses the wrapper, but can read unsanitized data within its authority.
3. **Disclosure enforcement:** if the agent must never see raw outputs or credentials, keep the gateway in a separate OS account/container and expose only a fixed stdio invocation. Deny direct cluster network access and filesystem access to gateway configuration/credentials. A local process launched under the same unrestricted user is not such an isolation boundary. A PATH alias, tool description, or agent instruction cannot replace it.

The supplied RBAC is an operator-reviewed starting point, not automatically applied policy. Remove unnecessary resources. Bind each namespace separately. Default examples never grant Secrets, ConfigMaps, exec, attach, proxy, port-forward, token creation, impersonation, or mutation. Optional cluster scope requires an additional binding and a config change. API discovery is not needed for these fixed paths. An unavailable catalog API version fails without fallback.

Before real deployment, an operator should verify both successful intended reads and denied mutations/secret reads using the actual dedicated identity, and inspect its other bindings. The tool does not run authorization checks or mint tokens itself. Kubernetes [RBAC documentation](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) describes resource/subresource permissions and wildcard risks.

## Credentials and subprocesses

Kubeconfig accepts one YAML/JSON document with `apiVersion: v1`, `kind: Config`, contexts, clusters, users, and empty optional preferences. Only static bearer tokens or client certificate/key pairs are supported. Certificate/CA files may be referenced; the loader reads them once and embeds their bytes. A direct HTTPS server origin is required; an omitted CA uses system certificate trust. Exec plugins, auth providers, impersonation, proxy URLs, insecure TLS, token files, extensions, duplicate named entries, unknown fields, and conflicting credential sources are rejected. These restrictions intentionally exclude ambient cloud login helpers; provision a dedicated read-only identity out of band instead.

All source configuration files are limited to 1 MiB. The configured context is selected once and rebuilt into a minimal in-memory snapshot. The original kubeconfig is never passed to kubectl. Changing it after startup cannot introduce a helper or new context. Restart after credential rotation; expiry results in an ordinary failure rather than fallback to another identity.

The runner clears the inherited environment, disables [kuberc preferences](https://kubernetes.io/docs/reference/kubectl/kuberc/), uses an isolated HOME/working directory/cache, closes stdin, caps combined stdout/stderr, bounds duration and concurrency, and never invokes a shell. macOS/Linux cancellation kills the process group. Windows terminates the direct process; helper execution is prohibited. The required Windows `SystemRoot` is inherited from the trusted launcher environment. No cloud credentials, proxy settings, loader/debug environment, or default kubeconfig are inherited by kubectl.

Temporary credentials use mode 0600 in a private temporary directory and are removed after normal execution. Unix modes do not configure Windows ACLs: provision a private, ACL-protected Windows service profile/temp root. Same-user processes, administrators, process-memory inspection, core dumps, and forced termination are outside this protection. A forced crash/kill can leave temporary files; operators should control and clean their service temp root. Neither secure erasure nor an OS sandbox is implemented.

For configuration trust, follow Kubernetes' [kubeconfig warning](https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/). Never accept config supplied by an untrusted repository or log message.

## Sanitization

All successful resource data is parsed as JSON, recursively scrubbed, then re-encoded. Unknown/malformed resource JSON is withheld in full; malformed log records are handled per line. Sensitive key matching normalizes case and separators. All environment arrays, generic `value` fields, annotations, commands/args, bodies, SQL fields, and several credential-bearing objects are replaced wholesale. JSON keys and embedded strings are scrubbed too. Deep objects are replaced after 64 levels; numbers retain their original JSON precision.

Log processing checks sensitive labels and continuation state before JSON suffix parsing. It withholds ambiguous physical lines with `[WITHHELD: ambiguous log fragment]`, preserving newline positions and independent neighboring records. Orphan indentation (including after recognized timestamps), bare/scalar values, unframed plaintext, unparseable structured fragments, and Python dictionary repr are withheld. Supported record envelopes include complete JSON objects, recognized timestamps/severity prefixes, logfmt metadata, and diagnostic prefixes. It never evaluates Python or other log content.

Quoted sensitive values and PEM blocks remain withheld until their closing delimiter. Apparent log prefixes inside such values cannot reset the state. If the closing delimiter is absent, subsequent lines in that ambiguous span are withheld through the end; preceding records remain. This replaces affected lines, never a whole successful dump with a single error. YAML-style blocks and indented continuations are also withheld. Valid structured JSON retains safe fields and diagnostics while sensitive fields are replaced.

Configured literal/pattern rules are applied to keys, strings, numeric/boolean/null scalars, and multiline matches. Equivalent bounded numeric exponent spellings are checked without losing unmatched number precision. Unreasonably large numeric representations are redacted when rules require classification. Configured rules cannot erase a sensitive label before built-in classification. Cross-line configured matches withhold only their intersecting physical lines. The selected kubeconfig token/key/certificate strings are included as literals. Redaction counts and optional `withheld_lines` are diagnostic counters, not proof that arbitrary output is secret-free.

The fixture corpus is synthetic, representing OpenSearch, RabbitMQ, Kvrocks, CNPG/Postgres, Python, cert-manager, external-dns, Prometheus/Alertmanager, Fluent Bit, Cilium, CoreDNS, and generic workload records. No proprietary log parser or dependency is required.

**Limits:** arbitrary short secrets, personal names, unlabeled values, URL path segments, SQL embedded in ordinary prose, unexpected multiline formats, encoded/compressed data, split records, confusable Unicode, and otherwise ordinary-looking, self-contained records whose external sensitivity context was removed by upstream tail/since selection can survive. Recognizably orphaned fragments from the audited cases are now withheld; this does not establish semantic knowledge of all application data. Entropy-like length rules are only heuristics. This is not a DLP guarantee. Avoid logging secrets at source; extend the corpus with representative approved samples and explicit literal/pattern rules. There is no raw-output switch.

Subprocess overflow, timeout, or cancellation discards the entire response. `kubectl --limit-bytes` is intentionally not used because it can cut a credential mid-record. Successful sanitization has a second serialized-envelope size check. Failed commands return sanitized stderr and a generic error; their potentially partial stdout is discarded. No tool output is persisted to logs by this application.

Sanitization is not prompt-injection prevention. Output is marked untrusted and the MCP server instructs clients to treat it as data; those hints cannot control an agent's other tools. The closed read policy still applies if the agent follows a malicious instruction found in a log.
